# Multithreading

A **multi-threaded** programming solution improves the elapsed time to complete execution by distributing independent tasks across separate hardware threads.

A program's performance can be described in terms of two aspects:

- tasks
- communications

**Tasks** involve executing instructions and require processor time. **Communications** involve transferring data between processors, memory, and external resources, which often causes delays because of higher latency. Communication with external resources has much higher latency than with main memory, leaving the processor idle while it waits. To use the processor efficiently, operating systems use multitasking: the processor switches between tasks or programs to minimize idle time.

## Multitasking vs multithreading

**Multitasking** manages multiple processes, which are independent instances of programs. A process includes all the information about its execution and can be blocked by the operating system if it requests a resource. Switching between processes (a context switch) is computationally intensive, requiring thousands of clock cycles.

**Multithreading** uses threads, which are lightweight, independent flows of control within a process. Threads share the same address space and can run concurrently. A context switch between threads is less intensive, requiring only hundreds of clock cycles.

Multitasking is managed by the operating system, while multithreading can be controlled within a process. Threads can be software (logical) or hardware (physical), and the scheduler maps software threads to hardware threads for efficient execution.

## Threads and synchronization

A process starts on a single thread but can spawn child threads to handle concurrent tasks. Threads synchronize at a **join point**, where one waits if the other hasn't completed its task.

## Shared memory and race conditions

Threads share memory, which adds complexity: concurrent threads can access and modify shared variables. This can cause **race conditions**, where the outcome depends on the order of execution, making results inconsistent. Shared states, mutexes, locks, and atomics help manage shared memory safely.

## Key techniques

- **Shared states**: let threads communicate using shared values.
- **Mutexes and locks**: prevent multiple threads from accessing shared memory at the same time by locking it during updates.
- **Atomics**: lock-free, indivisible execution of specific instructions.

## Deadlock

Occurs when threads wait indefinitely for one another, causing the system to halt.

## Policy-based execution in C++17

C++17 lets you choose **how algorithms execute**:

- Sequentially (one step at a time, on one thread)
- In parallel (multiple steps at the same time, using multiple threads)
- With vectorization (using hardware features to process multiple data points simultaneously)

### Execution policies

These are rules that decide how the program runs tasks:

1. **Sequential** (`std::execution::seq`)
    - Runs tasks one at a time, in the order they're written.
    - Example: a line of people waiting to buy coffee, served one by one.
2. **Parallel** (`std::execution::par`)
    - Runs tasks on multiple threads, splitting the work.
    - Example: multiple baristas serving customers at the same time.
3. **Parallel with vectorization** (`std::execution::par_unseq`)
    - Runs tasks using threads and also uses hardware features to do several operations at once.
    - Example: each barista uses both hands to serve two customers simultaneously.

### Example: summing numbers in a list

You have a list of 1 million numbers and want their total.

```cpp
#include <iostream>
#include <vector>
#include <numeric>
#include <execution> // For execution policies
int main() {
    std::vector<int> numbers(1'000'000, 1); // A million numbers, all set to 1

    // Sequential Execution
    int sum_seq = std::reduce(std::execution::seq, numbers.begin(), numbers.end());
    std::cout << "Sequential Sum: " << sum_seq << std::endl;

    // Parallel Execution
    int sum_par = std::reduce(std::execution::par, numbers.begin(), numbers.end());
    std::cout << "Parallel Sum: " << sum_par << std::endl;

    return 0;
}
```

- **Sequential**: adds the numbers one by one (slower).
- **Parallel**: splits the work across multiple threads, so it is much faster.

## Practice Questions

??? question "1. What are the two aspects of a program's performance?"

    **Tasks** (executing instructions, which need processor time) and **communications** (transferring data between processors, memory, and external resources, which adds latency).

??? question "2. What is the difference between multitasking and multithreading?"

    Multitasking manages multiple **processes** (independent instances of programs), managed by the operating system, and a context switch costs thousands of clock cycles. Multithreading uses **threads**, lightweight flows of control inside one process that share an address space, and a context switch costs only hundreds of clock cycles.

??? question "3. What is a race condition?"

    When concurrent threads access and modify a shared variable and the outcome depends on the order of execution, so results are inconsistent. Mutexes, locks, atomics, and shared states help manage shared memory safely.

??? question "4. What is a deadlock?"

    When threads wait indefinitely for one another, so none of them can proceed and the system halts.

??? question "5. What do mutexes and atomics each do?"

    A mutex (lock) prevents multiple threads from accessing shared memory at once by locking it during updates. Atomics provide lock-free, indivisible execution of specific instructions.

??? question "6. What are the three C++17 execution policies?"

    `std::execution::seq` (sequential, one at a time), `std::execution::par` (parallel, split across threads), and `std::execution::par_unseq` (parallel plus vectorization, using hardware to process several data points at once).
